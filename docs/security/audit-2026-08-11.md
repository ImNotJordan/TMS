# Security audit — 11 August 2026

Scope: every registered API route, the IAM grants held by the browser and the
server, the tenant model, and the stores behind each screen. Method was static
review plus live probing of the running dev server and the real AWS account.

Two findings were **proven against the live system**, not inferred. The rest are
backed by the policy JSON and the code paths cited.

A note on method: a UI click-through was not possible (no browser driver in the
environment) and would have been the weaker instrument anyway. Every finding
below is about what a caller *can* do, not what the UI *offers* — and the two
critical ones are reachable with `curl` and a valid session, no UI involved.

## 1. ~~Critical~~ FIXED (code) — the browser owns `UsersTable`

**Fixed in code, 12 August 2026.** All three readers moved behind
`/api/profile` and `/api/admin/audit`; none imports the DynamoDB SDK any more.
The audit trail is append-only (no PUT, no DELETE route) and partitioned per
company — it had also been readable across every tenant, which this finding did
not catch. The generated browser policy no longer contains the table.

> **Not closed until the browser policy is applied in AWS.** The code is correct
> and the deployed permission set is what an attacker sees. Verify with the
> **Simulate** button on the role: `dynamodb:Scan` on `table/UsersTable` must
> come back *denied*.

The original finding follows.


The Identity Pool authenticated role holds, with no condition:

```
dynamodb:GetItem, Query, Scan, PutItem, UpdateItem, DeleteItem
  on arn:…:table/UsersTable
```

Any signed-in user — including a Driver, the lowest-privilege role — can open
devtools and:

- **`Scan UsersTable`** and read every user in every company: name, email,
  phone, department, role, `companyId`, `employerCompanyId`. This bypasses
  `/api/admin/users` completely. The directory scoping built this week is a
  presentation control while this grant exists.
- **Write any row.** Including another user's `employerCompanyId`, which now
  decides directory membership, and their profile fields.
- **Delete the audit trail.** `recordAdminAuditLog` stores entries in this same
  table as `section: "log-*"` rows (`admin-audit-store.ts:229`). The record
  meant to catch abuse is editable by the people it would incriminate.

### Fix

Move the remaining `UsersTable` readers behind the server, then drop the table
from the browser policy entirely:

- `profile-store.ts` — `putOwnSection` is already shaped for it; `putSection`
  and `getAllSections` take an arbitrary `userId` and must not stay client-side.
- `admin-audit-store.ts` — append-only from the server. Audit entries should not
  be writable by the subject at all.
- `admin-users-store.ts` — `getAdminDirectoryUserById` still queries directly.

Until then, treat all profile data as readable by any authenticated user.

## 2. ~~Critical~~ FIXED (code) — the browser can rewrite the tenant claim

**Fixed in code, 12 August 2026.** Create-user, password reset and resend-invite
moved to `/api/admin/user-credentials`. The logic itself was not rewritten — it
moved to `cognito-admin-core.ts` with the credentials injected — because the
reset path branches on user status through three layers of fallback and two
copies would drift. Reset and resend now also require the target to be in the
caller's company, which the original grant never checked. No browser module
imports the Cognito admin SDK, and the browser policy has no Cognito statement.

> **Not closed until the browser policy is applied in AWS.** Verify with the
> IAM simulator: `cognito-idp:AdminUpdateUserAttributes` on the user pool must
> come back *denied*.

The original finding follows.


```
cognito-idp:AdminUpdateUserAttributes  on the user pool
```

`custom:companyId` is marked read-only on the app client. That setting governs
the **user-facing** `UpdateUserAttributes` call only. `AdminUpdateUserAttributes`
is an IAM-authenticated admin API and ignores it.

So any signed-in user can set their own `custom:companyId` to any value and read
that company's loads, carriers, quotes, invoices and CRM — through the API,
legitimately, because the server trusts the claim. That is the entire tenant
boundary, bypassed with one SDK call.

This grant exists only because create-user, password reset and resend-invite
still run in the browser (`cognito-admin.ts`).

### Fix

Move those three flows to server endpoints — the same pattern as
`/api/admin/user-role`, which already exists and does group management safely —
then remove `AdminCreateUser`, `AdminGetUser`, `AdminUpdateUserAttributes`,
`AdminSetUserPassword` and `AdminResetUserPassword` from the browser policy.

This is the single highest-value remaining task.

## 3. ~~High~~ FIXED — two unauthenticated endpoints (proven)

**Fixed 12 August 2026.** Both handlers now call `requireCurrentTenantContext`
as their first statement, before rate limiting and before the schema. Replaying
the exact requests below now returns 401. Regression tests assert both the
unauthenticated refusal and the check ordering, because a body-first handler
answers 400 to a malformed anonymous request and looks superficially guarded.

The original finding follows.


`handleCommsTranslateRequest` and `handleCommsAgentDraftRequest`
(`comms-proxy.ts:389`, `:418`) run rate limiting and schema validation, then do
the work. Neither ever checks a token.

Proven against the running server with no `Authorization` header:

```
POST /api/comms/translate       -> 200
  {"translatedText":"[es] proof of unauthenticated access",
   "engine":"ai:gpt-4o-mini", …}

POST /api/comms/agent/draft     -> 200
  {"draft":"Thanks for the update. …","confidence":0.72, …}
```

They returned 400 rather than 401 to an empty body, which is the tell: the body
was validated before anything checked who was asking.

Both are currently deterministic stubs, so today's impact is bounded. But the
response already advertises `engine: "ai:gpt-4o-mini"`, and `agent/draft`
accepts 8 KB of thread summary plus 4 KB of inbound text. The moment a real
model is wired in, this is unauthenticated spend on your OpenAI account, at a
rate limited only per-IP.

### Fix

Add the same guard the sibling handlers use, as the first statement in each:

```ts
const { tryVerifiedIdClaims } = await import("@/lib/ai/cognito-request-credentials");
if (!(await tryVerifiedIdClaims(request))?.sub) {
  return jsonError("Sign in required.", 401, "not_authenticated");
}
```

Auth belongs before rate limiting and before body parsing — an unauthenticated
caller should never reach a schema.

## 4. ~~High~~ FIXED — SMS send is authenticated but not authorized

**Fixed 12 August 2026.**

- **Authorization.** `authorizeSender` requires the caller to belong to a
  company. Drivers are tenant-exempt and carry none, so they are denied by
  construction rather than by a role list someone has to maintain. Applied to
  email as well as SMS, and checked before the rate limiter so a denied caller
  cannot consume anyone's budget.
- **Session freshness.** `requireCurrentTenantContext` replaced
  `tryVerifiedIdClaims`, so a token issued before a revocation is refused.
- **Rate limit** is keyed on the account, not the IP.
- **Sending identity** resolves per company from `TWILIO_FROM_NUMBERS` /
  `SENDGRID_FROM_EMAILS` (JSON maps of `companyId` → identity), falling back to
  the shared one with a warning naming the company. Every send is audited with
  actor, company, provider id and whether the shared identity was used.

**Still open:** the DNC check remains a substring match on `"dnc-block"`. Real
consent enforcement needs an authoritative store and is a compliance workstream
(TCPA), not a patch.

The original finding follows.


`handleCommsSmsSendRequest` (`comms-proxy.ts:199`) checks
`tryVerifiedIdClaims(request)?.sub` and nothing else. Any signed-in user, a
Driver included, can send SMS to arbitrary numbers through the company's Twilio
account.

Three separate gaps:

- **No role check.** Messaging customers is not a driver capability.
- **No tenant scoping.** There is one set of Twilio credentials in worker env,
  so every company sends from the same number. A message sent by one tenant is
  indistinguishable from another's, and the recipient sees a shared identity.
- **Rate limit is per-IP** (`enforceRateLimit` keys on `clientKey(request)`),
  not per-company or per-user. It does not bound what one tenant can spend, and
  a distributed caller escapes it entirely.

The DNC check is also a substring match on `"dnc-block"`, with a comment already
acknowledging real consent enforcement is missing. That is a compliance exposure
(TCPA) independent of the security issue.

### Fix

Gate on `requireCurrentTenantContext` plus a role check, key the rate limit on
`ctx.companyId`, and resolve the sending number per company rather than from a
single env var.

## 5. ~~High~~ FIXED — two companies named "HHI"

**Fixed 12 August 2026.** The duplicate itself was resolved through the UI —
`verify-driver-scoping.mjs` now reports one HHI and no duplicate names.

The root cause is closed too, which matters more: company identity was *derived*
from whatever directory the client happened to be showing, so an admin who could
not see the existing "HHI" minted a second one, and the server accepted the id it
was handed. `/api/admin/company-assignment` now refuses to create a **new**
company id under a name already in use, deriving the list server-side where the
caller cannot influence it (`tenant/known-companies.ts`). Assigning to an
existing company is untouched.

`scripts/merge-companies.mjs` handles any future occurrence: it moves records via
the `companyId-index`, then Profile rows, then the Cognito claim with a session
epoch bump — records first, so a moved user never sees an empty workspace.

The original finding follows.


Live data:

```
HHI    d06f5f2d-b15e-4b4b-b787-b4a5cc20a7f3   amilasan_jordan@…  + the driver
HHI    f6034de3-6093-4c3f-a754-5fd318e96b9a   aldwinraya@…
RAHYO  2fa966b7-7d9b-47d6-afd6-4cc70edbd6a2   j_amilasan@…
```

`aldwinraya@hyacinthindustriesllc.com` is in a different tenant from
`amilasan_jordan@hyacinthindustriesllc.com`. They cannot see each other's loads,
carriers, quotes or CRM. Nothing in the UI reveals this, because every screen
displays the name and records are keyed by the id.

This is the lightweight company model's failure mode: when a typed company name
does not match one already visible in the directory, a fresh id is minted.

### Fix

Decide which id is canonical, reassign the other users via Admin → Users → Edit,
and re-key any records already created under the losing id. `verify-driver-scoping.mjs`
now detects and reports duplicates.

## 6. Medium — drivers with no employer are invisible

The directory predicate fails closed for tenant-exempt roles: a Driver with no
`employerCompanyId` appears in no company's list. That is the intended
behaviour — the alternative was the bug where every company saw every driver —
but existing drivers predate the field.

### Fix

```
node scripts/backfill-driver-employer.mjs --company-id <id> --company-name "<name>" --apply
```

Currently one driver is affected and already has an employer set. Re-run
`verify-driver-scoping.mjs` after any bulk user import.

## 7. Low — no client-side route guards

No route under `src/routes/` uses `beforeLoad` or an auth wrapper. Unauthenticated
users can navigate to any page; it then fails on data load.

Not a security boundary — the server is — but it produces confusing error states
instead of a redirect to sign-in.

## What is working

Worth stating, because these were checked and are correct:

- **Twilio webhook signatures are verified** (`verifyTwilioSignature`), with a
  timing-safe comparison, and the handler refuses when the token is unset rather
  than skipping the check.
- **No secrets in `VITE_` variables.** Every one is a table name, region or pool
  id — all legitimately public. No API key is bundled into the client.
- **`USER_PASSWORD_AUTH` is disabled** on the app client, so the pool resists
  credential-stuffing and scripted login. It is also why the live privilege
  probe could not run; that trade is the right way round.
- **The server principal is denied `dynamodb:Scan`**, verified by
  `verify-server-principal.mjs`.
- **Fifteen tables are behind the API** with a lint rule preventing regression;
  `check-tenant-guard.mjs` reports no violations.
- **Role changes cannot be self-served** and privileged roles require platform
  admin in both directions.
- 390 tests pass; typecheck clean.
